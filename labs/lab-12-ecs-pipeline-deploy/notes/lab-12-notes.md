## Review Questions

**Q1. Three changes that cannot travel through the ECS deploy action, and how to deploy each.**
The action copies the running task definition and changes only the image, so (1) **CPU/memory changes**, (2) **new or changed environment variables or secrets**, and (3) **log configuration or health-check changes** cannot travel through it. Each is deployed by producing a new revision with describe → modify → register (Step 10) and `update-service` by hand, or better, by declaring the task definition as code (CloudFormation) so the whole document is versioned and deployed together; alternatively a pipeline step can register a full `taskdef.json` from the repository (the CodeDeploy blue/green action does exactly that).

**Q2. Are `GetAuthorizationToken` on `*` and `RegisterTaskDefinition` on `*` the same kind of exception?**
For "same": both are on `*` because there is no specific resource ARN to scope at request time: the token is registry-wide and a new revision does not exist yet. Against: `GetAuthorizationToken` only returns a credential; every useful follow-up action (push, pull) is still checked against the repository ARN, so `*` grants almost nothing on its own. `RegisterTaskDefinition` on `*` creates executable configuration with no further per-resource check on its contents, bounded only by PassRole and `UpdateService`'s scope. **My answer:** they are different in kind: the first is harmless by construction, the second is a real grant whose risk (Exercise 4) is only partly bounded.

**Q3. Digest vs tag.**
To a sceptic: a digest is the content's identity, so a task definition that names one deploys exactly the bytes that were tested; a tag can be moved by any later push, so "r7" today may not be "r7" at the next scale-out (Exercise 5 is designed to test this). The strongest case against pinning digests: you lose the ability to roll out a patched base image or security fix by re-pushing a tag; every fix, even an urgent CVE patch, needs a new task definition revision and a deployment, and digests are unreadable to humans, so reviewing "what are we running" becomes harder without tooling. Immutable, unique tags give most of the safety with readable names.

**Q4. A failure the circuit breaker would not catch.**
A release that starts, passes a shallow health check (e.g. `/` returns 200), but returns wrong data, e.g. enrolment requests silently fail against the database or a feature is broken. The breaker only watches task start-up and health checks. The mechanism that catches it is application-level monitoring: CloudWatch alarms on error rates / latency / business metrics, used by CodeDeploy's `DEPLOYMENT_STOP_ON_ALARM` auto-rollback during a blue/green traffic shift, plus deeper health checks and post-deploy smoke tests (the `AfterAllowTestTraffic` hook).

**Q5. What replace-only APIs have in common.**
Each manages a single document that is only meaningful as a whole (a pipeline's ordered stages, a bucket's notification set, a trust policy, a bucket policy), where validity depends on relationships between the parts (artifact names chaining stages, overlapping notification filters, statement interaction). Replacing the whole document makes the resulting state exactly what was sent and validation atomic. A merge-based `update-pipeline` would have to decide how to identify stages and actions (by name? position?), where a new stage goes, whether an omitted stage means "unchanged" or "delete", how to reorder, how to resolve artifact-name conflicts, and what happens when two concurrent edits merge into an invalid chain.

**Q6. Why `create-policy-version` is not `--set-as-default` by default.**
Because a policy is attached to live principals, and activating a version changes their permissions immediately. The design supports **stage, review, activate, roll back**: create the new version, inspect or test it (e.g. with the policy simulator), then switch the default deliberately; and if it breaks something, `set-default-policy-version` back to the previous version is instant, since the old version still exists.

**Q7. Which evidence settles "the service runs unreviewed code"?**
Once captured, `outputs/lab-12-deploy-evidence.txt` should link the execution ID to the deployed revision and its image URI. The pipeline execution history helps: it links the execution to the S3 source version it consumed. `outputs/lab-12-image-digest.txt` helps only partly: it is a local, editable file recorded outside the pipeline and it maps tags, not the running tasks. None of them links the running bytes to a *reviewed commit*. To settle it in one command I would need to record at build time the **source commit hash and its review/approval ID** together with the **pushed image digest** inside the image and the artifact (e.g. `build-metadata.json` + image labels) and pin the task definition to that digest, so `describe-task-definition` → digest → metadata → reviewed commit is a single lookup.
