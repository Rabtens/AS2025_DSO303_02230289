# Lab 04 - ECS on Fargate: Notes and Reflection

## 1. "I put auto scaling on the task definition"

That sentence is wrong in three ways. First, a task definition cannot be scaled at all: `usms-enrolment:1` is a read-only, versioned template that describes the image, CPU, memory, ports, log configuration and the two roles, but it contains no count. It cannot be modified, only replaced by registering a new revision. Second, auto scaling in Lab 06 is not attached to ECS directly but to an Application Auto Scaling *scalable target*, and that target is the service's desired count (`service/usms-ecs-cluster/usms-enrolment-svc`, dimension `ecs:service:DesiredCount`). Third, the scaling policy only ever changes that one number. It never launches or stops a task itself. The object that makes reality match is the ECS service, `usms-enrolment-svc`, whose scheduler constantly compares `runningCount` with `desiredCount` and starts or stops tasks until they are equal. This is exactly what happened when I ran `update-service --desired-count 3` by hand in Step 11: I changed the number, and the service did the work.

Because ECS itself knows nothing about the scalable target, nothing about scaling ever shows up in ECS. `describe-services` shows no policy, minimum or maximum. You just see `desiredCount` change and a service event saying tasks were started or stopped, with no explanation of why. To find the reason you have to ask a different service (`aws application-autoscaling describe-scaling-activities`). A practical consequence is that a manual `update-service --desired-count` can be silently overwritten by the next scaling action. Also, deleting the service does not delete the scalable target, which is left behind pointing at nothing.

## 2. One policy, two delivery mechanisms

`USMSStudentDataReadWrite` was written in Lab 1, before the bucket existed. It was attached to an EC2 instance through an instance profile in Lab 3, and attached unchanged to a Fargate task through a task role in this lab. On EC2, the instance profile makes the role available to the instance. At runtime the instance metadata service at `169.254.169.254` hands out temporary STS credentials for that role, and the SDK fetches them and refreshes them before they expire. On Fargate, ECS takes on the task role for each individual task and serves the credentials from the container credentials endpoint at `169.254.170.2`, whose path is given to the container in the `AWS_CONTAINER_CREDENTIALS_RELATIVE_URI` environment variable. The SDK's default credential chain picks them up in the same way. Neither mechanism needs a key on disk, because in both cases the credentials are short-lived, rotate automatically and are delivered by a local endpoint only the workload can reach. There is no permanent access key to copy, leak or rotate by hand. The main difference is scope: an instance profile is shared by every process on the instance, while a task role belongs to one task. The moment the bucket exists, nothing changes for either mechanism and the policy does not need editing. The policy names `arn:aws:s3:::usms-student-data` simply as text, and IAM does not check that the bucket exists when it evaluates the policy. Calls that previously failed with `NoSuchBucket` would simply start succeeding on both the EC2 instance and the Fargate task.

## 3. Execution role vs. task role

- **Task execution role broken:** the task never reaches RUNNING and stops with a reason such as `CannotPullContainerError` or a log-group error, so the container never starts at all.
- **Task role broken:** the task starts and runs normally, but the application's own S3 calls fail with `AccessDenied`.

Both roles share an identical trust policy because a trust policy only answers *who is allowed to take on the role*, not *what the role can do*. In both cases the role is taken on by the same service principal, `ecs-tasks.amazonaws.com`. What each role is allowed to do comes from its attached permission policies: the execution role has the ECS task execution permissions for pulling images and writing logs, while the task role has `USMSStudentDataReadWrite`. Which one is used for which job is decided by the field it is placed in within the task definition: `executionRoleArn` or `taskRoleArn`.

## 4. Why the enrolment rule is sourced from `usms-app-sg`

Sourcing the only inbound rule of `usms-enrolment-sg` from `usms-app-sg` is correct even if the task count never changed. The rule identifies the caller by *what it is* (a member of the web tier's group) rather than *where it happens to be* (an address). A CIDR block such as `10.0.1.0/24` would let in everything in the public subnet, including the NAT gateway and anything launched there later, not just the web tier. A single host IP would break as soon as `usms-web-01` was replaced, rebuilt from the golden AMI, or given a different private address. The group rule is therefore both tighter and more robust, and it states the actual intent: only the web tier may call the enrolment API on port 80.

Once Lab 06 lets the count change, this becomes close to mandatory. Every new Fargate task gets its own network interface with a fresh private IP taken from the private subnets, and tasks are constantly created and destroyed, possibly on the web-tier side as well. No one could keep an IP-based rule list up to date at that speed. With group references, a new task joins `usms-enrolment-sg` the moment its network interface is created, and the rule applies to it automatically without any edit.

## 5. What Fargate removes, and what it does not

Fargate removes the host layer of Lab 3's EC2 model. There is no AMI to choose or patch and no golden AMI to maintain. There is also no instance type to size, no root EBS volume, no key pair or SSH access, no ECS agent to run, and no work deciding which tasks fit onto which instances. I only declare CPU and memory (`256` / `512`) in the task definition, and AWS provides the compute.

What Fargate does not remove is networking and identity. Because the task uses `awsvpc` mode, each task gets its own network interface inside my own private subnets (`usms-private-subnet-a` and `-b`), with its own private IP and its own security group (`usms-enrolment-sg`), exactly like an EC2 instance. It also follows Lab 2's route tables. The image pull goes `usms-private-rt → usms-nat → usms-igw`, and S3 traffic goes through the gateway endpoint. If the NAT route were broken, the task would fail to pull its image just as an EC2 instance in that subnet would lose internet access. Subnet and AZ placement, security group rules, IAM roles, logging and the security of the container image itself all remain my responsibility.

## 6. Persistence: memory vs. hybrid mode

A command against this lab's resources that would look identical in both modes after a Floci restart is `aws ecs create-cluster --cluster-name usms-ecs-cluster`. Creating a cluster that already exists just returns it, so after a restart this returns an ACTIVE cluster in both modes. In memory mode it is a brand-new empty cluster, while in hybrid mode it is the existing one. The success tells me nothing about whether anything survived, which is the same trap as the unchanged account ID in Lab 1 Step 14.

A command that would *not* look identical is `aws ecs describe-task-definition --task-definition usms-enrolment:1` (or `describe-services` for `usms-enrolment-svc`). In hybrid mode it returns the task definition I registered before the restart, while in memory mode it fails because the resource no longer exists. A subtler version is to register the task definition again: hybrid mode gives `usms-enrolment:2`, but memory mode gives `:1` again because the revision counter was lost. The difference is that a check only proves persistence if its result depends on state created before the restart. Commands that recreate their own result, or always return the same answer, cannot tell the two storage modes apart.
