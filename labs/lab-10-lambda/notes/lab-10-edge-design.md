# Transcript delivery design

## Authorize before the cache lookup

I would use Lambda@Edge on **viewer request** to validate the signed session token locally using a trusted public key. It checks the issuer, audience, expiry, signature, and entitlement to the requested transcript before CloudFront can serve a hit. I would use short-lived tokens and overlap signing keys during rotation. The token check itself makes no origin or identity-provider call. Requests with invalid or missing credentials get a generic denial. The lab's student header would be replaced by this check. Both S3 origins would be private and allow CloudFront access through Origin Access Control. [CloudFront events](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/lambda-cloudfront-trigger-events.html)

## Cache immutable revisions

I would use a regional publishing function to write a corrected transcript under a new immutable revision key. It verifies that both origins can read the new object before activating the revision. A strongly consistent revision registry holds the current revision and a pending correction flag. The flag is set when the correction is accepted. If publication cannot complete in time, the viewer function must stop serving the old revision within five minutes and return a temporary error until the corrected copy is ready.

After authorization, the viewer-request function resolves the current revision and rewrites the stable transcript URI to that revision before the cache lookup. The registry is a separate metadata service and receives no transcript contents. Revision lookups may be reused locally for at most four minutes from the start of the last successful strongly consistent read. When that lease expires, a failed lookup returns a temporary error. I would reject viewer-supplied revision paths, so even an old URL cannot bypass the revision check. This design adds metadata reads while allowing unchanged transcript bytes to stay cached for hours. Corrected copies get a fresh cache key and do not depend on an invalidation completing on time.

The cache key is the canonical transcript ID and revision in the rewritten path. I would exclude session tokens, cookies, query strings, the caller's faculty, and other headers because authorized callers receive identical bytes for the same revision. I would use Lambda@Edge on **origin response** for the common security headers and shared-cache TTL. A CloudFront response headers policy can set private, no-store cache control for the viewer while retaining CloudFront's cache policy for the shared cache. I would test browser reloads and direct requests for superseded revisions as part of acceptance. [Edge trigger selection](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/lambda-how-to-choose-event.html)

## Keep downloads available during an origin outage

I would use a CloudFront origin group with private buckets in different Regions. Warm authorized requests can use CloudFront's cache. On a miss, CloudFront can retry transcript GET and HEAD requests at the secondary origin when the primary times out or returns a configured failure status. Both origins serve the same immutable revision keys. I would test that both paths deliver the same bytes and that neither serves the old revision after a correction. If neither origin can serve the current revision, I would return an error. [CloudFront origin failover](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/high_availability_origin_failover.html)

## Count refusals by faculty

The viewer function logs a structured denial with the request ID, timestamp, reason and faculty. Faculty comes from the transcript's trusted catalogue entry or from a verified claim where appropriate. Unknown faculty gets its own bucket, and the logs exclude tokens and student identifiers. Lambda@Edge logs land in CloudWatch Logs in the Regions where the function executes. I would collect those logs centrally and use a scheduled regional function to deduplicate by request ID and aggregate counts by faculty. This report is off the request path, so aggregation belongs in the Region. Edge logs are delivered on a best-effort basis, so I would label the counts as observed refusals and monitor delivery gaps. [CloudFront edge function logs](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/edge-functions-logs.html)

I would first measure correction-to-last-old-response time across several Regions under warm-cache conditions and repeat the test with the primary origin unavailable. If an old revision ever appeared at five minutes, I would shorten the metadata lease or remove local metadata reuse before deploying. I would also measure the metadata lookup rate and p95 latency to decide whether the four-minute reuse window is worth the complexity.
