# Lab 09 - Security Review: Notes and Review Questions

## Review Questions

1. Why is Step 18's "nothing broke" result strong, and describe a change that could have broken a verification script.

It is strong because Step 18 compares the *same five* verification scripts (Labs 02–06) against the summary lines recorded in Step 2, **before** any change. Identical output after rewriting egress, trust policies and keys shows those changes did not regress anything the earlier labs depend on, and the restart also proves everything persisted. A change that *could* have broken one: rotating the `usms-dev-01` access key and deleting the old key **before** repointing the `usms-dev` profile. Any script calling `--profile usms-dev` would then fail with `InvalidClientTokenId`. Another example is replacing `usms-enrolment-sg`'s allow-all egress with rules that forget the path to the ALB or S3, which on real AWS would break the Lab 04/05 health checks.

2. What changes about `usms-deploy-role`'s effective permissions if `USMSPermissionsBoundary` is attached as an ordinary policy instead of as a boundary?

As a **boundary**, `USMSPermissionsBoundary` is a ceiling. The effective permissions are the *intersection* of `USMSDeployBase` and the boundary, so the role can only do what both allow (the scoped ECS deploy actions and the scoped `iam:PassRole`). Attached as an **ordinary policy**, it becomes a *grant*, and identity policies are *unioned*. The role would suddenly get everything in its Allow statement: `ecs:*`, `elasticloadbalancing:*`, `logs:*`, `cloudwatch:*`, `s3:Get*/List*/PutObject`, and an **unscoped** `iam:PassRole` on `*`, which undoes the careful three-role scoping in `USMSDeployBase` (only the explicit Deny to EC2 would remain). There would also be no ceiling left, so any policy attached later would apply in full. The deny statements still apply in both cases.

3. Describe an incident where ingress rules are all correct but a breach still occurs, and say what egress control would/would not have prevented.

Example: the ingress rules are correct (only 80/443 to the ALB, the app tier only from the ALB group), but a dependency in the enrolment container is compromised through a supply-chain or deserialisation bug. The attacker never needs a new inbound path, because the malicious code opens an **outbound** connection to their own server on port 443 and sends the student data out, or pulls down a second-stage payload. With the default allow-all egress, that works. The Step 13 egress rule (tcp/443 only to the S3 prefix list) **would** have blocked a connection to an arbitrary attacker IP. It **would not** have stopped exfiltration *through* an allowed destination, for example `PutObject` into an attacker-owned S3 bucket over the S3 prefix list, or data hidden in DNS queries. Those need a VPC endpoint policy, an S3 bucket policy or DNS filtering.

4. Compare the blast radius of a compromised `sts:AssumeRole` for `usms-ecs-task-role`, `usms-transcripts-reader-role`, and `usms-deploy-role`.

**`usms-ecs-task-role`** (moderate): whoever assumes it gets what the running enrolment app has, which is read/write/**delete** on `usms-student-data` objects through `USMSStudentDataReadWrite`. They can damage the data but cannot change infrastructure or identities. **`usms-transcripts-reader-role`** (smallest): only `s3:ListBucket` + `s3:GetObject`, with an explicit Deny on every write. The damage is limited to *reading* transcripts, which is still a privacy breach, but nothing can be altered or destroyed. **`usms-deploy-role`** (largest): it can update ECS services and register task definitions, and it can pass three roles to `ecs-tasks`. An attacker could deploy their own container image and have it run *as* `usms-ecs-task-role`, getting that role's data access plus control of the application itself. The boundary and the scoped `PassRole` stop it from escalating further (no new users, keys, policy changes, or passing roles to EC2), which is exactly why the deploy role carries a boundary.

5. Why is "five controls" not simply five times better than "one control"? Is `usms-enrolment-sg` genuinely less protected than `usms-db-01`?

The controls are not equally strong and they are not fully independent, so you cannot simply multiply the protection by five. Several of them fail together: one mistaken console action or one misread template could add a public IP *and* an internet gateway route, and controls 1 and 2 (public IP and auto-assign) are really the same idea checked twice. What matters is how many *independent decisions* someone would have to get wrong. `usms-enrolment-sg` is protected mainly by one control (its security group admitting only the ALB group), which is why Step 17 calls it a single point of control. It is not necessarily *less protected* in practice, though. It is *meant* to be reachable from the ALB, it has no public IP, it sits in a private subnet behind the ALB, and it now has written egress. The difference is that a single mistake on its one security group exposes it, while `usms-db-01` needs several unrelated mistakes before it is exposed.

6. What do the extra two steps in the 4-step key rotation protect against? What would a real system use instead of a long-lived key?

Creating the new key first and **moving** every consumer to it (step 2), then **deactivating** the old key before deleting it (step 3), protects against **outage** and gives a **rollback path**. If some forgotten script, CI job or second machine still uses the old key, it breaks while the key is merely inactive, and `get-access-key-last-used` shows it. The key can be re-enabled in seconds, whereas a deleted key is gone forever. A two-step "create then delete" leaves either a window where nothing works or no way back. A real system would avoid long-lived keys entirely: **IAM roles with temporary STS credentials**, through instance profiles, ECS task roles, IRSA/EKS Pod Identity, or for humans **IAM Identity Center (SSO)** with short sessions and MFA. CI pipelines would use **OIDC federation** (for example GitHub Actions to `sts:AssumeRoleWithWebIdentity`).

7. Argue for or against: the review methodology (reading configuration, not testing) is an adequate substitute for demonstration. Name one defect each method catches that the other does not.

I would argue it is **adequate for this lab but not a full substitute**. Reading configuration covers every rule, including the ones nobody would think to test, and it is safe to run against production. Testing only proves the paths you thought to try. Reading catches, for example, the unused `s3:DeleteObject` grant or the missing `aws:SourceAccount` condition on a trust policy. No functional test would fail because of those, since the app never deletes and no confused deputy is attacking in a test. Demonstration catches what configuration *cannot* show: an emulator or service that does not actually enforce what the document says (Floci's `simulate-principal-policy` returning `implicitDeny` for an allowed action is a small example), a host firewall or application bug, or an egress rule that is syntactically right but breaks a real dependency such as the S3 endpoint. The strongest review does both: read to find what is wrong, then test to confirm the fix behaves as the document claims.
