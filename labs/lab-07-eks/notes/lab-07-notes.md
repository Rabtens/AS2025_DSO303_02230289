## Review Questions

**1.** An EKS cluster reports ACTIVE. Every pod sits in Pending. Explain why "the cluster is healthy" and "nothing can run" can both be true, and name two configurations that produce this symptom.

> ACTIVE only describes the control plane: the API server, etcd and the scheduler that AWS runs for me are up and accepting requests. Pods run on the data plane, the worker nodes, which is a separate thing I create and pay for. The scheduler can accept a pod and still find nowhere to place it, so the pod stays Pending. Two configurations that cause this: (1) no node group exists, or its nodes never joined because the node role is wrong or missing the worker-node/CNI permissions; (2) the nodes are Ready but the pods ask for more CPU/memory in `resources.requests` than any node can offer, which I reproduced as `FailedScheduling` in Step 19. A node group placed in subnets with no route to the control plane would also do it.

**2.** What would break if the cluster role and node role trust policies were swapped, and where would you notice it first?

> The cluster role would trust `ec2.amazonaws.com` and the node role would trust `eks.amazonaws.com`. EKS could not assume the cluster role, so it could not create the cluster's network interfaces or manage resources on my behalf. EC2 instances could not assume the node role, so they would get no credentials to register with the API server or pull images. I would notice it first at `aws eks create-cluster` (Step 8): on real AWS the call is rejected because the role cannot be assumed by EKS. Even if that got through, `create-nodegroup` would fail next, with nodes never becoming Ready.

**3.** Take either (Service vs Deployment) or (readiness vs liveness probe). Explain the distinction and describe a concrete failure from getting it backwards.

> A readiness probe answers "should this pod receive traffic right now?" If it fails, the pod is removed from the Service's endpoints but keeps running. A liveness probe answers "is this container stuck and in need of a restart?" If it fails, the kubelet kills and restarts the container. Getting them backwards: if I put a slow dependency check (for example "can I reach the database?") in the liveness probe, a short database outage makes every `usms-enrolment` pod fail liveness at once. All of them restart in a loop (CrashLoopBackOff) instead of just going temporarily not-ready, so one outage becomes two. The opposite mistake, only having a readiness probe on a deadlocked process, leaves a hung pod out of rotation forever, never restarted.

**4.** Step 18's rollback still reported version 1.1.0. Why? Argue for or against "Kubernetes rollback isn't really a rollback," and name the practice that resolves the problem.

> `kubectl rollout undo` only restores the previous pod template, the spec stored in the old ReplicaSet. `APP_VERSION` lived in the ConfigMap `usms-app-config`, which is a separate object with no revision history. The ConfigMap still said 1.1.0, so the "rolled back" pods started up and read 1.1.0 again. I would argue *for* the statement in a narrow sense: a Deployment rollback is a rollback of the Deployment, not of the application's whole state, so any config, Secret or database change outside the pod template stays forward. The practice that resolves it is **immutable, versioned configuration**: create a new ConfigMap per change (for example `usms-app-config-v2`, or a content hash in the name as Kustomize's `configMapGenerator` does) and reference it from the pod template. Then the config is part of the template and rolls back with it. Keeping all manifests in Git (GitOps) also means a real rollback is "revert the commit and re-apply".

**5.** `usms-enrolment` uses `maxUnavailable: 0`; `usms-results` uses the default (25%/25%). Describe what each does during an update, give one workload suited to each, and say which is closer to Lab 04's ECS deployment configuration.

> With `maxUnavailable: 0, maxSurge: 1`, `usms-enrolment` never drops below 2 ready pods. It starts one new pod, waits for it to pass readiness, then removes one old pod, and repeats. This is slower and needs spare capacity for the extra pod, but capacity never drops. It suits an API that must keep full capacity, like student enrolment during registration week. With the 25%/25% defaults, `usms-results` may take old pods down before their replacements are ready. That is faster and needs less headroom but can briefly reduce capacity. (At only 2 replicas, `maxUnavailable` 25% rounds *down* to 0 and `maxSurge` 25% rounds *up* to 1, so in this lab both services behaved alike; the difference shows at larger scale, e.g. with 8 replicas up to 2 can be unavailable at once.) Reduced capacity during an update is acceptable for a read-mostly or background workload such as a results viewer or report generator. `usms-enrolment` is closer to Lab 04's ECS setting of `minimumHealthyPercent` 100 / `maximumPercent` 200: ECS also starts the replacement task first and never undercuts the desired count.

**6.** Correct a colleague who says "it's a Secret so it's encrypted, safe to commit." What does a Secret actually provide, what doesn't it, and what would you use instead on real EKS?

> A Secret is only **base64-encoded**, not encrypted. I decoded `usms-enrolment-secret` with `base64 -d` in Step 17 in one line, so anyone who can read the YAML in Git can read the password. What a Secret does provide is a separate object type, so access can be limited with RBAC (who may `get secrets`). It also keeps sensitive values out of the pod spec and ConfigMaps, and it can be mounted as a file or env var. It does not provide encryption in the manifest, in Git, or (by default) in etcd, and it gives no rotation or audit history. On real EKS I would enable KMS envelope encryption of Secrets in etcd, and keep the real value in **AWS Secrets Manager** (or SSM Parameter Store). The pod would fetch it at runtime through the Secrets Store CSI Driver or External Secrets Operator, with IRSA so only that service account can read it. The Secret manifest itself should never be committed with real values.

**7.** For USMS specifically (small team, one region, quiet 8 months / busy 2), argue for ECS or Kubernetes. Name at least two things this lab was harder than Lab 04, and one thing Kubernetes gave you that ECS could not.

> I would choose **ECS** for USMS. It is a small team in one region, and the workload is mostly quiet with two busy months. ECS (especially on Fargate) gives that with no cluster to upgrade, no control-plane fee, and Service Auto Scaling that I already built in Lab 06. Things that were harder in this lab than in Lab 04: (1) two IAM roles (cluster and node) plus two trust policies, compared with ECS's task execution and task roles; (2) a second toolchain and kubeconfig (`kubectl`, contexts, namespaces) alongside the AWS CLI; (3) many more objects to write and keep consistent: Deployment, Service, ConfigMap, Secret and ServiceAccount for each microservice; (4) more failure modes to diagnose (ImagePullBackOff, FailedScheduling, CrashLoopBackOff). What Kubernetes gave me that ECS did not: built-in DNS service discovery by name with no load balancer in between, plus a readable revision history with one-command `kubectl rollout undo`. It also gave me portable manifests that would run on any conformant cluster, not just AWS. Those benefits matter more for a larger platform team or a multi-cloud requirement than for USMS today.
